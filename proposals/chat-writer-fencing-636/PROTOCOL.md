# #636 shared chat-writer fence — source proposal, NOT activated

API source: `e217c791d1735458b3720cebf4c923122f7df1dc`. Database source: `76bad6195b4bd1918284c5ebe49c91f408072ed2`. No Database AGENTS.md exists at that revision; root AGENTS, Database README and tests/README apply. Existing bounded DELETE runtime is API #1155. ## Decision and precise guarantee

Choose a persistent chat epoch plus immutable admission owner, enforced by service-only SQL commands and guards against legacy direct writes. All relevant operations take the same chat-row lock, after locking the owning session for share. A successful suffix delete increments the epoch, records tombstones and a retry receipt, and removes the scoped suffix in one transaction. A stale writer cannot commit a message mutation after that transaction; the original deleted message IDs cannot be inserted under a newer admission either. Newly admitted messages with new IDs remain possible. This is not a guarantee of exactly-once provider dispatch, cancellation, stream drainage, monotonic same-turn content, or atomic UI delete-plus-resend.

Alternatives considered: (1) a pending-delete CAS excludes some new starts but not old writes/headless starts and can wedge Stop/resume; rejected. (2) delete-only SQL locking closes no later writer path; rejected. (3) token checks in TypeScript without a shared database lock admit check/use races and legacy bypasses; rejected. (4) a hard offline drain with no persistent fence only gives the existing quiescent contract; insufficient. The selected design adds the minimal shared persistent authority needed for the stronger stale-writer invariant, with permanent identity tombstones because old message IDs otherwise can be replayed under a fresh token.

## Database boundary and ACL

`migration.sql` is deliberately outside `supabase/migrations`, so normal migration discovery cannot apply it. It is a draft executable proposal for disposable testing. It creates a dedicated NOLOGIN, non-superuser, non-BYPASSRLS owner; only this role owns SECURITY DEFINER functions. Qualified object references and empty search_path prevent search-path substitution. No caller role receives membership in it. Service role gets only RPC execute and read-only state access needed by invoker guards. Browser roles get neither. No caller-controlled GUC is an authority bypass. All guards, activation and command RPCs require READ COMMITTED before inspecting state; REPEATABLE READ and SERIALIZABLE are rejected, including on legacy writes to unenrolled chats, so pre-activation snapshots cannot miss enabled state. This installation-level compatibility constraint must be checked before approval.

`chat_fence_command(chat_id TEXT, effective_account UUID, action TEXT, payload JSONB)` is a trusted-service interface, not a client tool. The API must authenticate and authorize overrides using existing validateChatOwnership/auth context before calling. SQL rechecks and locks sessions.account_id against the supplied effective account. It does not accept an untrusted account as proof of org/admin membership. The service credential is trusted; a compromised trusted API can act for accounts it names, as with current service access. Database ownership/DDL privilege and superuser bypass are outside this runtime trust boundary and must not be held by service callers.

All stored chat/session/message IDs remain TEXT, matching the actual baseline. The API may retain its UUID input validation. Generations are integers bounded at JavaScript's maximum safe integer; exhaustion fails closed. Message created_at, role and chat identity cannot be changed by the RPC. Direct service message INSERT/UPDATE/DELETE, slot changes, identity moves, session ownership reassignment, parent cascades and TRUNCATE are rejected for enabled chats. State/receipts/tombstones are not caller-writable. Unfenced chats retain legacy behavior except serialization with activation; no global service table privileges are revoked. Cascades into enabled chats fail closed. Bulk backfill is deliberately unsupported on enabled chats: do not give a backfill the current epoch as a bypass.

RPC lock order: session share → chat update → state → message. Legacy direct UPDATE can already hold a message row before its trigger locks the chat; activation/mixed traffic can therefore deadlock. PostgreSQL aborts a participant; API must surface a controlled retryable conflict and never acknowledge success on an aborted transaction. A retry preserves the original request identity/epoch; it must not silently reacquire authority. Multi-chat legacy identity moves lock both chats in sorted order. New protocol commands operate on one chat.

## Commands and lifecycle

- `state`: returns the current epoch, owner, phase and real run ID. Read only after trusted auth. The value is observational; future writes require the captured token and atomic check.
- `admission_snapshot`: authenticated service-only lookup by request_id within the supplied chat/account; returns original receipt plus stored JSONB envelope/snapshot and exact canonical strings, including after close. Missing receipt raises P0002, never proof of no external start.
- `admit`: requires request_id UUID, expected_epoch, server-computed 64-character input_hash, admission_envelope, execution_snapshot, admission_canonical and execution_canonical. All immutable input is committed atomically with the receipt; hash-only admission is rejected. Locks state, requires idle/current epoch, increments epoch and records request/owner in pending phase. Sets active_stream_id to pending-owner. An exact retry returns its durable original receipt, including closed state and immutable original bound_run_id (null until binding); changed input fails. A receipt does not authorize blind redispatch.
- `bind`: requires exact epoch/owner and provider run_id. One run ID can bind a reservation. Identical binding retries succeed; other run IDs fail before provider/agent side effects. The bound run ID replaces the pending slot. Only the workflow journaled first step binds; remove route promotion CAS rather than layering it over binding. The route reads the original receipt and verifies owner/epoch before resuming an open run. Binding also persists bound_run_id in the admission receipt; release never clears it. Closed retries return that original run resource, never redispatch or substitute the live state run belonging to another admission.
- `write`: requires epoch/owner/run_id and a bound running reservation. Insert-only user messages accept only exact duplicates; assistant upsert can change only a message born in this epoch. Cross-chat ID collisions and all tombstoned IDs are rejected. New IDs get database timestamps. The stored parts value remains the full UIMessage object, with matching id/role and a nested parts array; it is not just that array. A surviving prior user ID may be acknowledged as an exact insert-only duplicate without mutation; a previous assistant ID cannot be overwritten. Regeneration must mint fresh IDs for every tombstoned message, including edited user messages, rather than reuse historical IDs. Return written:true and outcome:inserted|exactDuplicate|updated. Equal JSONB full envelopes are exactDuplicate and cause no message UPDATE; changed same-epoch assistant upserts are updated. This is an observation of this SQL invocation, not an exactly-once ancillary-effect receipt.
- `update_parts`: same immutable authority and scoped message identity; update only, never insert. Requires the message's birth epoch. Missing message returns updated:false; a stale token fails. Same-epoch last-writer semantics remain as before; this is not a content-revision merge algorithm.
- `release`: requires exact epoch/owner plus real run ID and either workflow_complete or external_terminal for running work. workflow_complete is trusted bound-workflow self-completion after all required writes have been awaited successfully; provider terminal status is neither required nor asserted. external_terminal is used only by Stop/reconciliation after external provider terminal evidence. SQL validates authority and the reason discriminator, not workflow control flow or provider evidence. Legacy terminal and timeout reason strings are rejected. Stale cleanup returns released:false and cannot clear a new owner. Pending release requires confirmed_no_start; a mere timeout is insufficient. Release closes the turn and invalidates outstanding writes through idle state. The API/workflow must await required persistence before releasing; rejected late persistence must be surfaced, not swallowed as success.
- `delete`: requires current expected_epoch, durable request_id and scoped anchor_id; requires idle authority and null legacy slot under lock. It stores an inclusive `(created_at,id)` suffix's IDs as tombstones, advances epoch, deletes and records its receipt atomically. Retrying the same deletion returns that receipt even after new admission, without deleting newer rows. Reusing a key for different input fails. No provider call or cancellation occurs inside SQL.

## Interactive/headless dispatch and crash retry

Both entry points must admit BEFORE message persistence, acceptance-dependent key minting, sandbox/skill/model effects or workflow start. Bootstrap exception: the authenticated session/chat identity rows must already exist for admission. New-chat enrollment remains a separately approved provisioning operation, never implicit in admit. This proposal deliberately scopes OUT global headless-provision retry deduplication: a retry that provisions a different chat is a different per-chat operation. It adds no durable account-scoped request-to-chat map and claims no exactly-once session/chat/sandbox provisioning. Every actual writer to an enabled chat must still use the fence. If the product requires one headless resource across new-chat retries, root must authorize a separate durable account-scoped mapping contract before claiming that guarantee. Carry `{chatId,effectiveAccount,epoch,owner}` in immutable durable workflow input; a missing token never becomes the current epoch. The workflow's first step binds its actual run ID before model, sandbox, persistence or other side effects. Initial user persistence moves inside the bound workflow and is awaited before agent execution; remove the current fire-and-forget route write. Headless starts cease being best-effort claim-after-start.

SQL and the workflow provider cannot share a transaction. A start whose response is lost may have created a workflow. Admission retry reads the stored binding: if bound and open, use the receipt original bound_run_id and verify matching live owner/epoch; if closed, return the original closed receipt/resource without redispatch; if still pending, do not automatically claim successful cancellation or clear it. Recovery may retry dispatch under the same owner; duplicate workflow instances must compete to bind and losers exit before side effects. This gives one database-authorized run, not exactly-once provider object creation. Runtime cutover is blocked until workflow-first binding is demonstrated on the real workflow model and loser cleanup cannot cancel or clear the winner.

A process death before transaction commit rolls back admission/deletion. A lost response after commit uses the same request ID/input to recover its receipt. No lease timeout automatically steals a reservation. Confirmed-no-start or terminal reconciliation is an authenticated service decision with evidence; ambiguous starts remain pending rather than fabricate a terminal outcome. Stale release and promotion never affect a newer owner.

Stop retains pending503, cancellation-failure502 and terminal-timeout504 behavior and preserves ownership on failure. It must use state/bound run identity and invoke owner-matching release only after terminal evidence. Resume reads phase: pending never calls getRun with the reservation string; running uses the bound real run ID; idle produces the existing finish-only behavior. Finally cleanup uses the original immutable token and workflow_complete only after successful required persistence. A rejected bind must bypass winner cleanup entirely: no release, stream close, winner cancellation or shared ephemeral-key revocation. Ambiguous start failures preserve pending ownership and key disposition; timeouts are not confirmed_no_start. This proposal does not claim provider cancellation success from an epoch update.

## Canonical admission hash v1 — adapter contract, not implemented in SQL

The trusted server hashes SHA-256 over UTF-8 canonical JSON of a versioned object: `contractVersion: "chat-admission/v1"`, effective account ID, session ID, chat ID, expected epoch, complete ordered UIMessage envelopes, resolved model and artist, interactive/headless mode, normalized dev-surface intent, and immutable execution-snapshot identity plus content digest. Include every additional execution-affecting option in that versioned object; changing the schema requires a new version. The snapshot must pin resolved sandbox/skills/model configuration and credential identity/account scope, never bearer bytes. Request ID keys the receipt separately; generation owner and provider run ID are assigned later and are not hashed.

Adapters must define a strict JSON-only schema: reject undefined, nonfinite numbers, unsupported values and unsafe integers; use explicit null for absent optional fields and normalize defaults once. Canonical encoding sorts object keys recursively by UTF-16 code-unit order, preserves array order and all string content without Unicode normalization, uses ECMAScript JSON string/finite-number encoding, and emits no whitespace. Full message metadata and data parts participate. The server stores the normalized envelope/snapshot reference durably before dispatch, and retries use that original immutable material. A changed supplied input under the same request ID fails; do not resolve mutable defaults, skills, secrets or model aliases again on an ambiguous retry. SQL validates lowercase hexadecimal digests, hashes the supplied UTF-8 strings, checks their parsed JSONB values against supplied objects, and binds scope/version plus receipt equality. It does not prove ECMAScript canonical encoding or the strict API content schema. The immutable snapshot persistence extension below supersedes the former hash-only storage limitation.

The API/UI adapter owner must qualify golden hash vectors (reordered object keys equal; array order/content/account/snapshot changes differ; defaults normalize once; bearer material absent), durable snapshot retrieval and first-step binding using the actual compiled SDK workflow. The adapter review at API e217c791d1735458b3720cebf4c923122f7df1dc / App 1581d6cc74544201da953fbf8122137adc9b9011 demonstrates metadata accessor and synthetic callback ordering only, not compiled replay or loser cleanup. No hosted feasibility claim is made here.

## Ancillary title/activity semantics and remaining technical disposition

Title and activity mutations are outside the message-fence invariant and outside the message-write transaction. An inserted result may schedule a conditional set-if-unset title; exactDuplicate must not guess that this caller inserted or emit a fresh activity event. updated means actual assistant content changed. Activity must derive from durable message state or use an idempotent event keyed by chat/message plus an explicit content version; replay must not advance wall-clock activity merely because the request retried. A lost inserted response followed by exactDuplicate cannot prove whether a title/event ran. Repair these ancillary effects from durable state or add a separately designed outbox if guaranteed delivery is required; this proposal does not add that guarantee. update_parts retains updated:false for missing and updated:true for existing authority-valid rows; it is not an insert/duplicate inference source.

Root technical disposition requested before adapters: accept the minimal per-chat headless retry scope (or separately commission provisioning mapping), the canonical v1 envelope/snapshot ownership and golden-vector qualification, and the conditional/repairable ancillary-effects semantics (or separately commission an outbox). These are explicit limits, not SQL proof gaps silently delegated to clients. Typed persistence failures, fresh IDs and immutable token propagation remain mandatory adapter requirements.

## Snapshot extension interface for API #1158 — proposed, unwired

Reviewed API foundation source ff2be8566344d96738552a06242612ab364aeb69 (tree 1a39c2b23f04c2afe6b0c0cabe08002482e8104d). This SQL interface intentionally requires a follow-up to its currently strict command schema; it does not change API code. Function signature remains `chat_fence_command(p_chat text, p_account uuid, p_action text, p jsonb)`.

`admit` payload fields are exactly the existing request_id, expected_epoch and input_hash plus admission_envelope (normalized object), execution_snapshot (object), admission_canonical (string) and execution_canonical (string). The admit result retains the existing receipt shape, excluding stored material; retrieve it with `admission_snapshot` payload `{request_id}`. Lookup returns `{receipt, admission_envelope, execution_snapshot, admission_canonical, execution_canonical}`. No caller receives direct table access. Lookup uses the same authenticated effective-account/session/chat locking boundary, and a request from another chat is not found even for the same account. Closed receipts retain original bound_run_id and original material while the current slot may belong to someone else.

The proposed snapshot outer object is `{contractVersion: "chat-execution/v1", id: string, effectiveAccountId: UUID-string, sessionId: string, chatId: string, requestId: UUID-string, content: object}`. API owns the strict schema for content and its resolved execution-affecting fields. SQL binds version/account/session/chat/request, requires a nonempty string ID and object content, and requires envelope.executionSnapshot.id to match. Snapshot identity is scoped to this chat/request, not a new global registry. A retry cannot rebind it to different bytes/content/digest. Another request may use its own snapshot identity; no cross-request snapshot deduplication guarantee is added.

The API canonicalizes the entire snapshot outer object with its strict encoder, computes UTF-8 SHA256, and supplies that digest in envelope.executionSnapshot.digest. It canonicalizes the full normalized admission envelope and supplies its SHA256 as input_hash. SQL hashes the exact supplied strings with built-in sha256(convert_to(text,'UTF8')), compares the declared digests and confirms each string parses to its paired JSONB value. It stores both original strings and JSONB objects atomically. It NEVER hashes JSONB serialization as a substitute. SQL does not enforce sorted keys, duplicate-key rejection, ECMAScript number encoding or all strict API JSON rules: canonical correctness is the trusted API producer/consumer contract. A consistent noncanonical encoding can pass SQL on a new request; API schema/canonicalizer must reject it before admission and again before dispatch. JSONB equality alone does not prove byte equivalence. Exact retries compare original strings as well as objects/hash; a different encoding under the same request conflicts even if its JSONB value is equal.

Before dispatch or recovery, API must validate strict schemas/version, re-encode both stored objects using its encoder, require exact equality with stored strings, verify both digests and account/chat/session/request scope, then materialize durable workflow input from that original material. Lookup errors are errors; they cannot trigger fresh-default resolution, changed scope, token refresh or blind redispatch. The envelope intentionally retains the existing API chat-admission/v1 shape without requestId; the snapshot binds requestId and its digest binds it transitively into the envelope hash.

No secret-store capability is added. Snapshot content may contain credential identity/account scope only, never service credentials, raw API keys, Privy tokens or bearer bytes. SQL scope/digest validation is not a secret detector for arbitrary JSON or user-authored message text. API's strict server-built snapshot schema must exclude secret fields and must never pass DurableAgentContext wholesale. Immutable snapshots can contain private message/context data and stay inside the private service-only schema; retention/deletion remains a separate design. Credential materialization/recovery remains blocked pending a reviewed identity-bound facility.

Root/API interface disposition needed: accept the two supplied canonical-string fields, lookup result shape and chat-execution/v1 outer identity envelope. API owner must add strict content schema and cross-language API-generated vectors; Python fixtures here use simple ASCII JSON and prove SQL byte binding, not equivalence with the TypeScript encoder. Existing compiled local SDK proof remains separate from SQL persistence and does not qualify credentials or hosted behavior. Runtime wiring is still blocked until snapshot/credential design review. No automatic migration, schema application or activation is authorized.
